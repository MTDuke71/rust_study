## 🎯 Problem Summary

**Title**: Movie Theater (Rectangle Area Maximization)

**Part 1**: Find the largest rectangle using any two of 496 red tiles as opposite corners (unconstrained).

**Part 2**: Connect the 496 points into a polygon, flood fill the interior with green tiles, find the largest rectangle containing only red/green tiles (polygon-bounded).

**Answers**:
- Part 1: **4,759,531,084** tiles
- Part 2: **1,539,238,860** tiles (32.4% of Part 1)

## 📊 Input Characteristics

**496 Red Tile Coordinates**:
- X range: [1,712, 98,484]
- Y range: [1,528, 98,072]
- Bounding box: 96,772 × 96,544 = **9.36 billion cells**

**Polygon Shape** (discovered via visualization):
- Nearly perfect **circle** with radius ~48,386 tiles
- Perimeter: ~304K theoretical, **588,656 actual** (via Bresenham)
- Interior area: π × r² ≈ **7.4 billion tiles**

## 🛠️ Solution Evolution

### **Part 1: Brute Force (Instant)**

```rust
fn find_largest_rectangle(points: &[(i64, i64)]) -> (usize, (i64, i64), (i64, i64)) {
    let mut max_area = 0;
    let mut best_pair = ((0, 0), (0, 0));
    
    // Try all pairs of points as opposite corners
    for i in 0..points.len() {
        for j in i+1..points.len() {
            let (x1, y1) = points[i];
            let (x2, y2) = points[j];
            
            // CRITICAL: Inclusive counting (+1 to width/height)
            let width = (x2 - x1).abs() + 1;
            let height = (y2 - y1).abs() + 1;
            let area = (width * height) as usize;
            
            if area > max_area {
                max_area = area;
                best_pair = (points[i], points[j]);
            }
        }
    }
    
    (max_area, best_pair.0, best_pair.1)
}
```

**Complexity**: O(n²) = 122,760 pairs
**Performance**: Milliseconds
**Result**: Points (83188, 85814) and (14596, 16427) → **4,759,531,084 tiles**

**Geometric insight**: Largest rectangle is a **diagonal square** spanning the circle's diameter (68,593 × 69,388).

#### **✅ Attempt 4: AABB Sampling (SUCCESS)**

**Reddit breakthrough**: *"Use AABB collision or compacted space"*

```rust
fn rectangle_in_polygon_optimized(
    x1: i64, y1: i64, x2: i64, y2: i64,
    boundary: &HashSet<(i64, i64)>,
    polygon: &[(i64, i64)]
) -> bool {
    let width = (x2 - x1 + 1) as usize;
    let height = (y2 - y1 + 1) as usize;
    
    // Adaptive sample rate: larger rectangles need more samples
    let sample_rate = max(10, max(width, height) / 100);
    
    // 1. Check corners (most critical)
    for &(x, y) in &[(x1,y1), (x2,y1), (x1,y2), (x2,y2)] {
        if !is_valid_point(x, y, boundary, polygon) {
            return false;
        }
    }
    
    // 2. Sample edges at intervals
    for x in (x1..=x2).step_by(sample_rate) {
        if !is_valid_point(x, y1, boundary, polygon) 
        || !is_valid_point(x, y2, boundary, polygon) {
            return false;
        }
    }
    
    // 3. Sample left/right edges
    for y in (y1..=y2).step_by(sample_rate) {
        if !is_valid_point(x1, y, boundary, polygon) 
        || !is_valid_point(x2, y, boundary, polygon) {
            return false;
        }
    }
    
    // 4. Sample interior grid
    for x in (x1..=x2).step_by(sample_rate) {
        for y in (y1..=y2).step_by(sample_rate) {
            if !is_valid_point(x, y, boundary, polygon) {
                return false;
            }
        }
    }
    
    true
}
```

**Performance**:
- Sample rate for 89K × 17K rectangle: 893
- Points sampled: ~2,244 (vs 1.54 billion!)
- Total operations: 122,760 rectangles × ~2K samples × 496 edge checks = **~633 million**
- Runtime: **3-5 seconds** ✅
- **Speedup: 3,650x** over naive approach

**Geometric insight**: Largest Part 2 rectangle is a **wide horizontal band** through center (89,340 × 17,229) - circular constraint forces different strategy than Part 1.

## 🧠 Key Algorithms Used

### **1. Bresenham's Line Algorithm**

**Purpose**: Generate discrete polygon boundary from 496 points

```rust
fn build_polygon_boundary(points: &[(i64, i64)]) -> HashSet<(i64, i64)> {
    let mut boundary = HashSet::new();
    for i in 0..points.len() {
        let (x1, y1) = points[i];
        let (x2, y2) = points[(i + 1) % points.len()];
        
        for point in bresenham_line(x1, y1, x2, y2) {
            boundary.insert(point);
        }
    }
    boundary
}
```

**Result**: 588,656 boundary tiles (vs 304K theoretical circumference)

**See**: [[bresenham-line-algorithm]]

### **2. Ray Casting Point-in-Polygon**

**Purpose**: Determine if a point is inside the polygon without materializing interior

```rust
fn point_in_polygon(point: (i64, i64), polygon: &[(i64, i64)]) -> bool {
    let (px, py) = point;
    let mut inside = false;
    
    for i in 0..polygon.len() {
        let (x1, y1) = polygon[i];
        let (x2, y2) = polygon[(i + 1) % polygon.len()];
        
        if (y1 > py) != (y2 > py) {
            let x_intersect = (x2 - x1) * (py - y1) / (y2 - y1) + x1;
            if px < x_intersect {
                inside = !inside;
            }
        }
    }
    
    inside
}
```

**Complexity**: O(n) per point, n = 496 edges
**Key insight**: Odd crossings = inside, even = outside

**See**: [[ray-casting-algorithm]]

### **3. AABB Sampling**

**Purpose**: Validate large rectangles by checking strategic sample points instead of all tiles

**Sample strategy**:
1. **4 corners** (most likely to violate constraints)
2. **Edge samples** at intervals (fail fast on partial overlap)
3. **Interior grid** at sparse intervals (confirm full containment)

**Adaptive rate**: `max(10, max(width, height) / 100)`
- Small rectangles: minimum 10 samples
- Large rectangles: logarithmic scaling

**See**: [[aabb-sampling-optimization]]

### **4. Sparse Data Structures**

**Purpose**: Store only polygon boundary, compute interior membership on-demand

```rust
// ✅ Sparse boundary storage
let boundary: HashSet<(i64, i64)> = build_boundary();  // 589K × 24 bytes = 14 MB

// ❌ Don't materialize interior
// let interior: HashSet<(i64, i64)> = flood_fill();  // 7.4B × 24 bytes = 178 GB

// ✅ Compute membership when needed
fn is_valid_point(x, y, boundary, polygon) -> bool {
    boundary.contains(&(x, y)) || point_in_polygon((x, y), polygon)
}
```

## 🎓 Learning Highlights

### **Mission Integration Lessons**

**Mission 6 (Grid) applicability**:
- ✅ **Perfect for**: Small examples (8 points, 11×11 grid)
- ❌ **Not viable for**: Large sparse spaces (496 points, 96K×96K grid)
- 🎯 **Takeaway**: Use Mission concepts (flood fill theory) even when Grid struct doesn't scale

**The Integrator Approach**:
- Don't reinvent geometric algorithms - use proven components
- Understand when mission infrastructure applies vs when to pivot
- Combine multiple techniques: Bresenham + Ray Casting + AABB Sampling

### **Algorithm Evolution Documentation**

**Why document failures?**
1. **Educational value**: Shows why naive approaches fail at scale
2. **Pattern recognition**: Memory crashes → check input scale first
3. **Community learning**: Others face same issues, documentation helps
4. **Future reference**: When similar problems arise, know what NOT to try

**The Journey**:
1. Dense Grid → 37GB crash → **Check input scale before choosing structures**
2. Sparse Interior → 18GB crash → **Even sparse structures have limits**
3. Naive Ray Casting → Timeout → **Strategic sampling beats exhaustive iteration**
4. AABB Sampling → Success → **Community hints are valuable**

### **Input Scale Awareness**

**CRITICAL LESSON**: Always inspect actual input before implementing:

```rust
// ❌ Don't assume example scale matches real input

// ✅ Check input first
let (min_x, max_x, min_y, max_y) = find_bounds(&points);
let width = max_x - min_x + 1;
let height = max_y - min_y + 1;
eprintln!("Grid would be {} × {} = {} cells", width, height, width * height);
// → "Grid would be 96772 × 96544 = 9,345,245,985 cells"
// → Time to pivot to sparse representation!
```

### **Geometric Algorithms vs Grid Materialization**

**When to use geometric algorithms**:
- Large coordinate spaces (> 10K range)
- Low occupancy (< 1% of cells filled)
- Computed properties (point-in-polygon) vs stored state
- Continuous shapes (circles, polygons) vs discrete grids

**When to materialize grids**:
- Small bounded spaces (< 1000×1000)
- High occupancy (> 10% filled)
- Frequent random access to same cells
- Cellular automata with state evolution
