### Rayon Parallelization Deep Dive
**The Perfect Storm for Parallelization**:
- Part 2 runs 442 independent beam traces (all edge positions)
- Zero shared state between traces
- Embarrassingly parallel problem
- Simple change: `.iter()` → `.par_iter()`

**Performance Analysis**:
```rust
starts.par_iter()  // 442 starting positions
    .map(|&(pos, dir)| trace_beam(&grid, pos, dir))  // Independent
    .max()  // Streaming reduction, not materialized Vec
```

**Key Insights**:
- Rayon's `.max()` is a terminal reduction - doesn't store all 442 results
- Each thread maintains local max, merged at end
- On i7-13700KF (16 cores, 24 threads): ~18 traces per thread
- 11.67× speedup indicates memory/cache pressure as bottleneck

## 🔧 **Technical Insights**

### Zero-Cost Abstractions in Practice
**Enum Memory Layout**:
- `Direction`: 1 byte (4 variants compile to integers 0-3)
- `Tile`: 1 byte (5 variants compile to integers 0-4)
- `(Coord, Direction)`: 24 bytes (16 + 1 + 7 padding for alignment)
- Max state space: 111×110×4 = 48,840 states × 24 bytes = 1.17 MB (fits in L3 cache)

**Pattern Matching Efficiency**:
```rust
match (tile, dir) {
    (Tile::MirrorForward, Direction::Up) => vec![Direction::Right],
    // ... compiles to efficient jump table
}
```
At runtime: Simple integer comparisons, no overhead from type safety

### Mission 6 Coordinate System
- `Coord::new(x, y)` where **x = column, y = row**
- `(0, 0)` is **upper-left corner** (standard screen coordinates)
- Direction offsets: Up=(0,-1), Down=(0,1), Left=(-1,0), Right=(1,0)
- Mapping: Old (row, col) → New `Coord::new(col, row)`

### Beam Tracing Algorithm
**Dual HashSet Pattern**:
- `seen_states: HashSet<(Coord, Direction)>` - Cycle detection
- `energized: HashSet<Coord>` - Spatial coverage

**Why direction matters**: Same tile can be visited from 4 different directions
- Only cyclic if `(position, direction)` pair repeats
- Prevents infinite loops in mirror/splitter configurations

**Termination conditions**:
1. Out of bounds (beam exits grid)
2. Cycle detected (seen this exact state before)

### Hypothetical: Beam Collision Physics
**Why parallelization would break**:
- Time-stepped simulation creates sequential dependencies
- Tick N+1 depends on collision outcomes from tick N
- Can't compute future without past (unlike current independent traces)
- Would need synchronization barriers between time steps
- Limited parallelism: only within single tick, not across ticks

**Typical AoC escalation pattern**:
- Part 1: "Count energized tiles" (spatial, final state)
- Hypothetical Part 2: "Count beams at step 1,000,000" (temporal, requires cycle detection)
- Eric's signature move: scale-up that forces algorithmic pivot
