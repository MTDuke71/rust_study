## ⚡ **Major Accomplishments**

### AoC 2022 Day 8 — Grid Visibility
99×99 grid of tree heights ('0'-'9'). Two related problems:
- **Part 1**: Count trees visible from outside (any direction)
- **Part 2**: Find maximum scenic score (product of viewing distances in 4 directions)

**Implementation**: Straightforward directional iteration with `Vec<Vec<u8>>` for grid storage.

**Answers**: Part 1: 1,690 | Part 2: 535,680

**Runtime**: 483µs (0.483ms) — current slowest day but still well under 1ms

**Optimization Applied**: Ring-based early termination — reduced to **445µs (7.5% improvement)**
- Group trees by minimum edge distance (center = d=49, edge = d=0)
- Process from center outward
- Calculate theoretical max score per ring: `d² × (98-d)²`
- Skip remaining rings when theo_max ≤ current_best
- Result: Skipped ~27% of trees (rings d=0 to d=8)

## 🔧 **Technical Insights**

### Simplicity Over Components
Initially planned to use **Mission 6's Grid<T>** (integrator approach), but Mission 6's API uses `Coord` types and `(x, y)` coordinates which added complexity for row-first parsing. Opted for simple `Vec<Vec<u8>>` instead.

**Trade-off**: Mission integration teaches validated component reuse, but simple `Vec<Vec<u8>>` was more natural for this problem's row-first parsing and indexing pattern.

### Visibility vs. Viewing Distance
- **Part 1**: Binary check — is tree visible from ANY direction?
  - Check left/right/up/down: all trees shorter?
  - Edge trees always visible
  
- **Part 2**: Count viewing distance — how far can you see in EACH direction?
  - Walk until edge OR tree >= height
  - **Include** the blocking tree in count
  - Scenic score = product of 4 directions

### Directional Iteration Pattern
Used signed offsets `(dr, dc)` for 4 directions: `(-1,0)` up, `(1,0)` down, `(0,-1)` left, `(0,1)` right. Single `viewing_distance()` function handles all directions, avoiding code duplication.

### Ring-Based Mathematical Pruning
Applied optimization: trees at edge distance `d` have theoretical max score = `d² × (rows-1-d) × (cols-1-d)`. By processing center→edge and calculating theoretical max per ring, we can skip outer rings once current best exceeds their potential. Trade-off: ring grouping overhead (~50µs) vs. skip checking ~2,700 trees (~38µs savings net).

**Why modest improvement?** Setup cost (Vec allocations) + cache locality disruption (ring order vs row-major) eat into savings. Still demonstrates valuable pruning technique for search problems.
