## ⚡ **Major Accomplishments**

### AoC 2022 Day 8 — Grid Visibility
99×99 grid of tree heights ('0'-'9'). Two related problems:
- **Part 1**: Count trees visible from outside (any direction)
- **Part 2**: Find maximum scenic score (product of viewing distances in 4 directions)

**Implementation**: Straightforward directional iteration with `Vec<Vec<u8>>` for grid storage.

**Answers**: Part 1: 1,690 | Part 2: 535,680

**Runtime**: 483µs (0.483ms) initial → **174µs final (2.8× speedup)**

**Optimizations Applied**:

**v2: Ring-based early termination (Part 2)** — reduced to 445µs (7.5% improvement)
- Group trees by minimum edge distance (center = d=49, edge = d=0)
- Process from center outward
- Calculate theoretical max score per ring: `d² × (98-d)²`
- Skip remaining rings when theo_max ≤ current_best
- Result: Skipped ~27% of trees (rings d=0 to d=8)

**v3: Pre-compute max heights (Part 1)** — reduced to 262µs (41% improvement, 1.7× from v2)
- **Key insight**: O(N³) → O(N²) complexity reduction
- 4 directional passes to compute max heights from each edge
- Visibility becomes O(1) check: `height > max_from_any_direction`
- Part 1 time: 180µs → 80µs (100µs saved)
- **Trade-off**: 4 extra grids (~40KB) for major time savings

**v4: Rayon row-based parallelization (Part 2)** — reduced to 174µs (33% improvement, 1.5× from v3)
- **Key insight**: Multi-core parallelism using Rayon library
- Process each row in parallel: `(0..rows).into_par_iter()`
- Part 2 time: 167µs → 94µs (44% speedup)
- **Trade-off**: Gave up ring early termination for multi-core execution
- **Failed first attempt**: Ring-based parallel = 920µs (3.5× slower!) — thread overhead dominated
- **Lesson**: Parallelization needs large enough work units to amortize thread spawning costs

## 🔧 **Technical Insights**

### Simplicity Over Components
Initially planned to use **Mission 6's Grid<T>** (integrator approach), but Mission 6's API uses `Coord` types and `(x, y)` coordinates which added complexity for row-first parsing. Opted for simple `Vec<Vec<u8>>` instead.

**Trade-off**: Mission integration teaches validated component reuse, but simple `Vec<Vec<u8>>` was more natural for this problem's row-first parsing and indexing pattern.

### Visibility vs. Viewing Distance
- **Part 1**: Binary check — is tree visible from ANY direction?
  - Check left/right/up/down: all trees shorter?
  - Edge trees always visible
  
- **Part 2**: Count viewing distance — how far can you see in EACH direction?
  - Walk until edge OR tree >= height
  - **Include** the blocking tree in count
  - Scenic score = product of 4 directions

### Directional Iteration Pattern
Used signed offsets `(dr, dc)` for 4 directions: `(-1,0)` up, `(1,0)` down, `(0,-1)` left, `(0,1)` right. Single `viewing_distance()` function handles all directions, avoiding code duplication.

### Ring-Based Mathematical Pruning
Applied optimization: trees at edge distance `d` have theoretical max score = `d² × (rows-1-d) × (cols-1-d)`. By processing center→edge and calculating theoretical max per ring, we can skip outer rings once current best exceeds their potential. Trade-off: ring grouping overhead (~50µs) vs. skip checking ~2,700 trees (~38µs savings net).

**Why modest improvement?** Setup cost (Vec allocations) + cache locality disruption (ring order vs row-major) eat into savings. Still demonstrates valuable pruning technique for search problems.

### Pre-Compute Optimization (Major Win)
After ring optimization showed limited gains, applied **pre-compute max heights** for Part 1 visibility checks:

**Algorithm**:
1. Four directional passes (left→right, right→left, top→bottom, bottom→top)
2. Build `max_from_left`, `max_from_right`, `max_from_top`, `max_from_bottom` grids
3. Tree visibility = O(1) check: `height > ANY max from edges`

**Impact**: 
- Part 1: 180µs → 80µs (100µs saved, 2.25× speedup)
- Total: 445µs → 262µs (41% improvement)
- **Complexity**: O(N³) → O(N²) for visibility checks

**Trade-off**: Memory (~40KB for 4 grids) for major time savings. Worth it — benchmarks confirm 41% speedup.

**Edge case lesson**: Edge trees must be handled explicitly (always visible) — initial implementation missed this and failed tests (returned 19 vs 21).

### Rayon Parallelization (Multi-Core Win)
After precompute optimization, explored **Rayon** for multi-core parallelism:

**First Attempt - Ring-based Parallel** (❌ FAILED):
- Applied `.par_iter()` to ring processing
- Result: 920µs (3.5× slower than sequential!)
- **Why it failed**: Thread pool overhead (50-100µs per spawn) × thousands of tiny tasks >> speedup gained
- Each tree = ~30-40 operations, not enough work to justify thread spawning

**Second Attempt - Row-based Parallel** (✅ SUCCESS):
- Process entire rows in parallel: `(0..rows).into_par_iter()`
- Result: 174µs (1.5× faster than sequential 262µs)
- **Why it worked**: 
  - Larger work units: 99 rows, each with ~99 trees = ~9,000 operations per task
  - Better cache locality: sequential column access within rows
  - Optimal granularity: 99 tasks maps well to modern CPUs (8-16 cores)
- Part 2: 167µs → 94µs (44% speedup)

**Lesson Learned**: 
- Parallelization isn't always faster — work unit size must amortize thread overhead
- Row-level parallelism (99 tasks) beats tree-level (9,801 tasks) or ring-level (50 tasks with varied sizes)
- When in doubt: benchmark before committing to parallel approach
