## 🔧 **Technical Insights**

### Memoization Overhead Trade-off
**Critical Discovery**: Memoization is **slower for small inputs** due to HashMap overhead!

**Observed Performance**:
- **Length 5-9 chars**: Memoization 0.2-0.8x "speedup" (actually slower!)
- **Length 11-13 chars**: Break-even point (~2-5x speedup)
- **Length 15+ chars**: Exponential benefits kick in (14.9x → 132.4x → 279.8x)

**Why This Happens**:
1. **HashMap operations cost time**: Hashing strings, lookups, insertions
2. **Small problems succeed quickly**: Naive recursion finds answer fast, doesn't hit exponential wall
3. **Insufficient redundancy**: Only 10-21 unique substrings cached, not revisited enough times
4. **Constant overhead dominates**: For tiny inputs, O(1) HashMap operations > O(P^L) exponential growth

**Practical Implications**:
- Real AoC Day 19 inputs are 60+ characters → memoization absolutely essential
- For simple examples in tutorials, naive appears faster but doesn't scale
- This demonstrates why **algorithmic analysis beats microbenchmarks** - Big-O predicts scaling, not constant factors

### Static vs Dynamic Dispatch - Measured Performance Reality
**Rust for Rustaceans Ch2.2a: Dispatch Mechanisms benchmark results**

**Debug Mode** (1M iterations of `area()` calculation):
- Static dispatch: 3.8ms
- Dynamic dispatch: 4.1ms
- **Overhead: 9% slower** (1.09x)
- Vtable lookup adds ~0.3ns per call

**Release Mode** (same benchmark):
- Static dispatch: 383.8µs
- Dynamic dispatch: 378.2µs
- **Result: Essentially identical** (within measurement noise)
- Difference: 5.6µs over 1M calls = 0.0056ns/call

**Critical Insights**:
1. **Real work dominates**: When functions do actual computation (floating-point math), dispatch overhead is negligible
2. **Modern CPUs are fast**: Branch predictors and L1 cache make vtable lookups nearly free
3. **Release optimizations**: Both dispatch methods compile to near-identical performance
4. **Don't prematurely optimize**: Choose dispatch based on architecture needs, not theoretical overhead
5. **Benchmarking matters**: Release mode reveals that "dynamic is slow" is folklore for modern CPUs with real workloads

**When Dynamic Dispatch Would Be Slower**:
- Calling trivial/empty functions (vtable overhead = 100% of call time)
- Tight loops with no actual work
- Without release mode optimizations

**Architectural Decision Guide**:
- Use **static dispatch** (`<T: Trait>`) when: Types known at compile time, want maximum inlining
- Use **dynamic dispatch** (`dyn Trait`) when: Heterogeneous collections, plugin architectures, flexibility matters
- Use **enum dispatch** when: Fixed set of types, want manual control, avoid vtable

**Mission Applications**:
- Mission 8 BFS uses static dispatch for flexibility across graph types (not performance)
- Future plugin systems should use `dyn Trait` without guilt
- Measure before optimizing - dispatch is rarely the bottleneck
