## Technical Notes
- **Part 1**: direct `Vec::insert` simulation, buffer ≤ 2018 elements, O(N²) but tiny
- **Part 2 Insight #1**: index 0 is frozen — insertions always land at pos ≥ 1 after
  the first step, so the value "after 0" is literally the value at index 1.
  No buffer needed; just track the last `i` where the insert lands at index 1.
- **Part 2 Insight #2**: when `pos + steps < i`, no wrap occurs and the insert
  lands at index `pos+1` (never 1). Those iterations are irrelevant and fold
  into a single arithmetic jump: `k = ⌈(i-pos-steps)/steps⌉`, then
  `pos += k*(steps+1); i += k`.
- Wrap iterations run ≈ `steps · ln(N/steps) ≈ 4,300` times instead of 50M.

## Key Insight
**Simulate → observe invariant → skip.** Once I saw that position 0 never moves,
the 50M-element buffer collapsed to a single scalar. Then spotting that only
wrap iterations can ever write to index 1 turned the 50M loop into ~4,300
wraps. Two independent optimisations stacking multiplicatively — the kind of
win you only find by asking "which iterations actually matter?" before
reaching for Rayon or `FxHashMap`.

Naive 50M-iteration loop: 123.56ms. Batched version: 131.84µs. **937× speedup
from arithmetic alone** — no parallelism, no data-structure swap.

## Math Foundations Integration
Created [[harmonic-series-and-logarithmic-growth]] — the first math-foundations
note on asymptotic series. Day 17's 17-hits-in-50M observation is a crisp
empirical validation of $\sum 1/i \approx \ln(N/\text{steps}) \approx 11.7$.
Also captures the **log-log perception trap**: $1/x$ densities look evenly
spread on log-x axes because their cumulative is linear there, but in linear
reality 10 of 17 hits fall in the first 0.02% of iterations. This is
Benford-like front-loading, the same phenomenon that makes work-saving
batching optimisations possible (Day 17's 937× speedup = converting
$O(N)$ iteration into $O(\text{steps} \cdot \ln(N/\text{steps}))$).
