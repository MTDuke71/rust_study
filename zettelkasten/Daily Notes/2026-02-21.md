## Day 21: Monkey Math

**Problem**: ~2,800 monkeys form an expression tree. Each either yells a number or computes an operation on two other monkeys' values. Part 1: evaluate `root`. Part 2: `root` becomes equality check, find what `humn` must yell.

### Results
- **Part 1**: 160,274,622,817,992 (recursive tree evaluation) - 32µs
- **Part 2**: 3,087,390,115,721 (algebraic inversion walk) - 217µs
- **Combined**: ~499µs

### Algorithm: Recursive Evaluation + Inversion Walk

**Part 1** is straightforward recursive evaluation — each monkey resolves to a number by evaluating its dependencies depth-first. No memoization needed because the dependency graph is a tree (each monkey computed exactly once).

**Part 2** uses algebraic inversion:
1. Determine which branch of `root` contains `humn`
2. Evaluate the other branch to get the target value
3. Walk from `root` toward `humn`, inverting each operation

The key trap is non-commutative operations. When `humn` is on the right:
- `k - right = target` → `right = k - target` (NOT `target - k`)
- `k / right = target` → `right = k / target` (NOT `target / k`)

### Design Decision: Zero-Copy Parsing
Used `Monkey<'a>` with `&'a str` references borrowing directly from input — no String allocations for the ~2,800 monkey names. Combined with HashMap for O(1) lookup, this keeps parse time at 156µs.

## Patterns Worth Remembering

- **Expression tree = recursive HashMap lookup**: Pattern matching on `Monkey::Num` vs `Monkey::Op` with `monkeys[name]` lookup is clean and O(n) total
- **Single unknown → walk and invert**: No symbolic algebra needed — just propagate target values downward
- **Non-commutative trap**: `a - b` and `a / b` invert differently depending on which side is unknown. This is the #1 bug source in these problems.
- **Zero-copy with lifetimes**: `&'a str` in enum variants keeps parsing allocation-free while HashMap remains ergonomic
