## 🔧 **Technical Insights**

### Spatial Indexing Pattern for Grid Lookups
**Problem**: Original solution had O(gears × numbers × adjacency_calc) = millions of operations  
**Solution**: Build `HashMap<Coord, NumberId>` spatial index  
**Result**: O(numbers × digits + gears × 8) = ~160K operations  
**Measured Speedup**: **246.8x faster** (88.92ms → 360.25µs)  
**Benchmark Method**: Created `bench_day03` comparing both implementations across 100 iterations

**When to Apply**:
- Grid problems requiring "what entity is at this coordinate" queries
- Reverse lookups more efficient than forward iteration
- Repeated spatial queries on same dataset

**Implementation Pattern**:
```rust
// Build index once: O(n × d) where n=entities, d=coords per entity
let mut coord_to_entity: HashMap<Coord, usize> = HashMap::new();
for (id, entity) in entities.iter().enumerate() {
    for coord in entity.occupied_coords() {
        coord_to_entity.insert(coord, id);
    }
}

// Query many times: O(1) per lookup
for point_of_interest in pois {
    for neighbor in point.neighbors_8() {
        if let Some(&entity_id) = coord_to_entity.get(&neighbor) {
            // Found entity at this coordinate instantly
        }
    }
}
```

**Trade-offs**:
- Memory: O(total_coordinates) for index
- Build time: One-time O(n×d) cost
- Lookup time: O(1) amortized across many queries
- **Break-even**: Worth it when queries > entities

### HashSet vs Vec for Set Operations
- **Vec.contains()**: O(n) linear search
- **HashSet.insert()**: O(1) with deduplication
- Use HashSet when checking membership repeatedly
- Use Vec when order matters and no duplicates expected
