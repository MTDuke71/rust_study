## Technical Insights

### Rayon for MD5 Mining (Again)
Third MD5 mining problem in AoC 2016 (Days 5, 13-formula, 14). Same pattern applies:
- Each hash computation is independent → embarrassingly parallel
- Rayon `into_par_iter()` distributes across cores with minimal code change
- Part 2's key stretching (2017× MD5) makes parallelization essential: ~5.7s → ~571ms

### Hash Caching for Lookahead Windows
The 1000-index lookahead creates overlapping windows between candidates.
Without caching, hash `N+500` would be recomputed for every candidate
between `N-500` and `N`. A simple `Vec<String>` cache ensures each hash
is computed exactly once, with batch pre-computation via Rayon.

### Generic Hash Function Pattern
```rust
fn find_64th_key<F>(salt: &str, hash_fn: F) -> u64
where F: Fn(&str, u64) -> String + Sync
```
The `+ Sync` bound is the only addition needed for Rayon compatibility.
Same matching logic handles both plain and stretched hashing.

### Borrow Checker vs Closures
Initial attempt used a closure capturing `&mut cache` that also returned `&str`
references into the cache — classic "captured variable cannot escape FnMut" error.
Solution: pass `&mut cache` as an explicit parameter instead of capturing it.
