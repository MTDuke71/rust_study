## 🔧 **Technical Insights**

### **Problem Type Recognition is Critical**
- Part 2 is **NP-hard Integer Linear Programming** - requires specialized solvers, not search algorithms
- State space analysis revealed why search fails: Machine 3 has 9 counters with targets [168, 164, 176...] → billions of states
- BFS passed all test cases but actual input timeout exposed scalability issues

### **Floating-Point Precision Matters**
- **Bug**: `minilp` returns 16756.999... which truncates to 16756 with `as usize`
- **Fix**: Use `.round() as usize` instead → correct answer 16757
- **Lesson**: Always round floating-point solver results, never truncate

### **Native Dependencies are Painful**
- Attempted Z3 SMT solver (`z3 = "0.12"`) - requires libclang.dll, CMake, Visual Studio Build Tools
- Compilation failed on Windows with "couldn't find libclang.dll"
- **Solution**: Use pure Rust alternatives - `good_lp` with `minilp` feature compiles out-of-the-box

### **Mathematical Formulation**
```rust
// ILP Model for Part 2:
Minimize: Σ x_i (total button presses)
Subject to:
  For each counter j: Σ (a_ij * x_i) = t_j
  x_i ≥ 0, x_i ∈ ℤ (non-negative integers)
```

### **Why ILP Succeeds Where Search Fails**
- Polynomial-time LP relaxation + branch-and-bound
- Handles 157 machines instantly vs search timeout on machine 3
- Solver exploits problem structure (linear constraints) that search algorithms don't
