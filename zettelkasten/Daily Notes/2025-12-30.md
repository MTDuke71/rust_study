## 🔧 **Technical Insights**

### Array Type Syntax and Destructuring
**Q: What does `[i32; 2]` mean?**
- **Array type**: `[i32; 2]` = "array of exactly 2 integers"
  - `i32` = element type
  - `2` = fixed compile-time length
- **Destructuring pattern**: `fn from([x, y]: [i32; 2])` unpacks array into variables
- **Key distinction**:
  - `From<(i32, i32)>` - converts from **tuple** `(3, 4)` (parentheses)
  - `From<[i32; 2]>` - converts from **array** `[3, 4]` (square brackets)

**Example:**
```rust
impl From<[i32; 2]> for Point {
    fn from([x, y]: [i32; 2]) -> Self {
        Point { x, y }  // x and y destructured from array
    }
}
let p = Point::from([3, 4]);  // Creates Point { x: 3, y: 4 }
```

### Why Fundamental Types Are Special
**Q: Why are `&`, `&mut`, `Box<T>` special for the orphan rule?**
- They're **transparent wrappers** - don't change the fundamental identity of the type
- Marked with `#[fundamental]` in compiler - orphan rule "looks through" them
- `&T`, `&mut T`, `Box<T>` just change **storage/access semantics**, not what type you're working with

**Without fundamental types being special:**
```rust
impl Debug for &LocalType { ... }  // Would be REJECTED
// Reasoning: "& is from std, Debug is from std, both foreign!"
```

**With fundamental types:**
```rust
impl Debug for &LocalType { ... }  // ACCEPTED
// Reasoning: "& is fundamental (transparent), LocalType is local!"
```

**Why this design?** References and boxes are core to Rust's ownership - forcing wrapper types would be impractical.

### Orphan Rule Core Principle
**Q: What's the fundamental rule?**
**"At least one must be yours"** - either trait OR type (or both) must be defined in your crate

```
✅ Local Trait + Local Type     = VALID
✅ Local Trait + Foreign Type   = VALID  
✅ Foreign Trait + Local Type   = VALID
❌ Foreign Trait + Foreign Type = INVALID ("can't glue two strangers together")
```

**Special cases that extend this:**
- `impl ForeignTrait for &LocalType` ✅ (fundamental type is transparent)
- `impl From<LocalType> for Vec<String>` ✅ (covered implementation - local type "covers")

**Why?** Prevents conflicts when two crates both try to implement same foreign trait for same foreign type.

### Mission 11 Lifetime Safety Deep Dive
**Q: Why don't `patterns` need lifetime `'a`?**
- `patterns` only used for **comparison** (`strip_prefix(pattern)`)
- **Never stored** in the cache
- Cache keys derived from `design`, not `patterns`
- Independent lifetimes: `patterns` can be destroyed after function returns

**Q: Do patterns live longer than design?**
- **Don't know, don't care!** They're independent
- Function works regardless of relative lifetimes
- No lifetime annotation = "only needed during function call"

**Q: Design must live as long as memo?**
- **Exactly!** Lifetime `'a` enforces this contract
- `design: &'a str` + `memo: HashMap<&'a str, bool>` = same lifetime
- Compiler prevents dropping `design` while `memo` has references to it
- Zero-cost abstraction - compile-time verification only

**Q: Cache outliving function - contradiction?**
- **No!** String literals are `'static` - live forever
- `let design = "wrr"` → variable dropped, but data permanent
- `let design = String::from("wrr")` → would fail, data freed when dropped
- `'static` satisfies any lifetime requirement (outlives everything)
