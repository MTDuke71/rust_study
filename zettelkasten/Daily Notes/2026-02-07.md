### AoC 2022 Day 7 — Stack-Based Size Accumulation
Parsed `cd`/`ls` terminal output to compute directory sizes. The key insight: **we don't need a tree or directory names**. cd/cd.. commands naturally form a stack of running totals.

## 🔧 **Technical Insights**

### "Do I need the names?"
The HashMap version stored directory path strings that nobody ever queries. The problem asks for *sizes*, not "which directory." Stripping the keys gave 23× speedup. **General principle**: before choosing a data structure, ask what information you actually need to answer the question.

### Stack Matches DFS
Terminal output IS a depth-first traversal. `cd` = go deeper, `cd ..` = backtrack. Using a HashMap fights the natural structure; using a stack embraces it.

### Three Consecutive Optimization Wins
- Day 3: HashSet → Bitset (15×)
- Day 6: Rebuild → Rolling XOR (2.4×)
- Day 7: HashMap → Stack (23×), then parse-once (2×) = 49× total
- **Pattern**: In each case, questioning the data structure yielded massive speedups.

### Parse-Once Pattern
Following the established pattern from Days 1, 4, 5 — compute_dir_sizes() once in solve(), pass Vec<u64> to both parts. Avoided redundant line parsing, stack operations, and string slicing. "Don't do work twice when you can share the result."
