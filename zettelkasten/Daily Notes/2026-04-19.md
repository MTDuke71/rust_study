## Technical Notes
- **One traversal, two answers**: the letters and the step count are both
  side effects of the same walk. The internal primitive is
  `walk() -> (String, usize)`; the public `solve_part1` / `solve_part2`
  just project the tuple. Combined bench ≈ single walk (not 2× single walk).
- **`Option<Coord>` unifies move + bounds**: `step()` returns `None` for
  both "off-grid" and "blank space" — the main loop and the corner-probe
  logic both use the same predicate. No bespoke look-ahead.
- **Pad-then-index**: ragged rows (trailing spaces stripped) are rectangularised
  at parse time with `row.resize(width, b' ')` so every subsequent `grid.get`
  returns a meaningful byte. Avoids a per-read guard in the hot loop.
- **Crossings are implicit**: a `|` over `-` is not a `+`, so the match arm
  for `|`/`-` (`_ => {}`) passes through unchanged. No special "crossing"
  code path — the problem shape pays the invariant for you.

## Key Insight
**Don't split when the work is already joint.** The obvious shape for an AoC
day with two parts is `solve_part1()` and `solve_part2()` as independent
functions. But when both answers come from the same traversal — like this
one — that shape doubles the runtime for nothing. The refactor is to make
the internal function return `(Part1, Part2)` and have the per-part wrappers
just take the `.0` or `.1`. The benchmark numbers make this legible:
`day19_part1` and `day19_part2` each run the whole walk (~85µs); `day19`
combined runs it **once** (~90µs). If I'd structured it the other way,
combined would have been ~170µs.

Mission 6's `Grid<u8>` + `Coord` shaved the "bounds-check every get" cost
into the parse step. The hot loop is four lines: match on tile, maybe turn
or collect, attempt step, update or break. That's the payoff of reusable
components — the per-day code shrinks to just the problem logic.
