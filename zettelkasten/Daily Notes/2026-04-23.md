## Technical Notes
- **Tiny VM**: 8 registers `a..h` (all i64, start 0), four opcodes `set/sub/mul/jnz`.
  No `add` — the program adds by subtracting negative literals (`sub b -100000`
  is really `b += 100000`). This is the subtle bit when extracting constants
  from the parsed AST: flip the sign on every `sub X -N` literal.
- **Part 1 closed-form check**: with a=0, the setup block is skipped and
  b = c = 93, so the outer loop runs exactly once and the `d/e` double-loop
  executes `(93-2)² = 8281` multiplications. The test answer matches the
  closed form exactly — nice confidence check that my VM simulator is right
  before trusting it on Part 2.
- **Part 2 analytical rewrite**: the program with a=1 is
  ```python
  for b in range(109300, 126300+1, 17):      # 1001 values
      if any(d*e == b for d in range(2, b) for e in range(2, b)):
          h += 1
  ```
  That's naïve primality by trial multiplication, O(b²) per value. Replace
  with O(√b) trial division; total work drops from ~10¹³ to ~1.7×10⁵ ops.
- **`extract_bounds` reads the parsed AST**: rather than hardcoding
  `(109300, 126300, 17)`, read them from `instrs[0], [4], [5], [7], [30]`
  so the solver works on any user's input. A `test_bounds_match_setup_simulation`
  test cross-checks `extract_bounds` by actually simulating the first 8
  instructions with `a=1` and comparing registers — catches layout drift.
- **Parse-once honored**: `solve()` parses once and calls both `_with_data`
  helpers. Combined (116.07µs) ≈ sum of individual parts (115.48µs) + one
  parse, matching the repo's convention.

## Key Insight
**On bytecode puzzles, the VM is a red herring — the *program* is the problem.**
Part 2 of Day 23 gives you an ISA and a 32-line program that would take hours
to run straight, and the author all but says out loud: "Technically, if it had
that, it wouldn't even need to run the program." The solve is to open the
assembly file, recognise that the `d/e` double-loop is `∃ d, e ∈ [2, b): d*e = b`
(i.e., naive primality by trial multiplication), and compute what it's trying
to compute — *directly*.

This is the exact trap pinned in the `feedback_aoc_bytecode_puzzles` memory
from earlier puzzles: for a custom-ISA problem, dig into the hidden program,
not just the ask. Day 23 rewarded that discipline with a 5×10⁸× speedup (hours →
26µs). The same pattern shows up in [2015 Day 23](https://adventofcode.com/2015/day/23),
various Intcode puzzles in 2019, and several LLVM-IR–style CTF puzzles: the
ISA is a delivery mechanism; the *program* encodes a mathematical routine;
the solve is to recognise the routine and replace it.

The second piece worth naming is that `extract_bounds` reads from the parsed
AST rather than the puzzle prose. Every user's AoC input has the same program
shape with different constants — five literal slots in a fixed layout.
Extracting from `Instr::Set(_, Value::Num(n))` makes the solver portable
across inputs and puts the "layout assumption" on a test (`test_bounds_match_setup_simulation`)
where it can fail loudly rather than silently returning the wrong answer.

Combined with the sign-flip on `sub X -N` (the ISA's "add in disguise"), this
was a clean study in AST-walking small DSLs — a muscle that'll come up again
in Project Euler's primality-heavy early problems, and (eventually) any
tutorial-level interpreter work in the rust-study track.
