### Algorithmic Insights

#### 1. Factor Elimination Strategy
**Problem**: Trial division tests many candidates unnecessarily

**Solution**: Divide out each factor completely before continuing
```rust
while n % f == 0 {
    n /= f;  // Shrinks n, loop terminates early
}
```

**Impact**: 600B → 8.4B → 10M → 6,857 in ~4,000 iterations (not 775,146!)

#### 2. Integer vs Floating-Point Comparison
**Naive**: `f <= (n as f64).sqrt() as u64` (slow, precision loss)

**Optimal**: `f * f <= n` (fast integer multiplication, always exact)

**Speedup**: ~10-15× faster comparison + auto-updates as n shrinks

#### 3. Remainder-is-Prime Theorem
**Discovery**: After dividing out all factors ≤ √n, any remainder > 1 is prime

**Impact**: No primality test needed! Algorithm itself proves remainder is prime.

**Proof**: If remainder were composite, we would have found its factors earlier (contradiction)

#### 4. Tool Selection Maturity
**Considered**: Pollard's Rho (advanced factorization for large semiprimes)

**Rejected**: Overkill for this problem (small first factor 71 found in ~36 iterations)

**Principle**: Use simplest tool that works (YAGNI - You Aren't Gonna Need It)

**When Pollard's Rho shines**: Large semiprimes (product of two huge primes) in cryptography

#### Intra-Workspace Dependencies

**Concept**: Workspace members can depend on each other using path dependencies

**Pattern**:
```toml
# In advent_of_code/aoc2023/Cargo.toml
[dependencies]
mission6 = { path = "../../missions/Mission6" }
mission8 = { path = "../../missions/Mission8" }
```

**Benefit**: Reusable mission components in AoC solutions (e.g., Day 10 using Grid + Graph)

**Critical Gotcha - Mixing Dependency Sources**:

**Problem**: Same crate from different sources = incompatible types!

```
Scenario: 
- Local workspace has mission6 at path "missions/Mission6"
- External crate depends on mission6 = "1.0.0" from crates.io
- Cargo sees TWO DIFFERENT mission6 crates:
  - mission6(path)::Grid
  - mission6(crates.io)::Grid
- Compiler error: "expected Grid, got Grid" (confusing!)
```

**Why**: Cargo identifies crates by **source + name + version**
- Different source = different crate ID = incompatible types
- Even if code is identical!

**Solution**: **Never mix sources** for same crate
- ✅ All path: `mission6 = { path = "..." }`
- ✅ All crates.io: `mission6 = "1.0.0"`
- ✅ Override with `[patch.crates-io]` if needed
- ❌ Mix path + crates.io: Type mismatch errors!

**Current workspace status**: Safe - all dependencies are path-based, no mixing!

#### Dependency Resolver Versions

**Workspace uses `resolver = "3"`** - cutting edge! 🚀

**Evolution**:

**Resolver v1** (Pre-2021):
- Feature pollution: If any crate enables a feature, ALL crates get it
- Dev-dependencies leak features to main code
- Problem: Unnecessary features everywhere

**Resolver v2** (Rust 2021+):
- Per-target feature resolution
- Build script isolation
- Dev-dependencies don't affect regular builds
- Default for edition 2021

**Resolver v3** (Rust 1.78+, May 2024):
- **MSRV-aware dependency resolution** (major improvement!)
- Respects `rust-version` field in Cargo.toml
- Automatically picks dependency versions compatible with minimum Rust version
- Prevents "requires Rust X.Y" errors when you specified older MSRV

**Example**:
```toml
[workspace]
resolver = "3"

[workspace.package]
rust-version = "1.75.0"  # Minimum supported Rust version

# Cargo will NOT pick dependencies requiring Rust 1.76+
# Even if newer versions exist!
```

**Why we're using v3**:
- ✅ Latest stable (Rust 1.78+)
- ✅ Backward compatible with v2
- ✅ More correct dependency resolution
- ✅ Future-proof (will be default in edition 2024)
- ✅ No downsides

**Benefit**: If missions are published, users with older Rust can still use them!
