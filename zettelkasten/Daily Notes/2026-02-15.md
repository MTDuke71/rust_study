## 💡 Solution Approach

### Key Insight: Interval Merging, NOT Grid Storage

**The problem**: Grid coordinates span millions (y up to 4,000,000)
**Naive approach**: Materialize 4M × 4M grid (16 trillion cells!) ❌
**Smart approach**: Interval merging ✅

**Algorithm**:
1. Calculate Manhattan distance from sensor to beacon (radius)
2. For target row y, calculate X-coverage interval for each sensor
3. Sort and merge overlapping intervals
4. Count positions or find gaps

**Why this works**: Sparse coverage → intervals are much smaller than full grid!

---

### Part 1: Single Row Coverage (237ns!)

**Algorithm**:
```rust
fn count_impossible_positions(sensors: &[Sensor], target_row: i32) -> usize {
    // 1. Calculate X-intervals at target_row
    intervals = sensors.filter_map(|s| {
        radius = manhattan_distance(s.pos, s.beacon);
        vertical_dist = |s.y - target_row|;
        remaining = radius - vertical_dist;

        if remaining >= 0 {
            Some((s.x - remaining, s.x + remaining))
        } else {
            None  // Sensor doesn't reach this row
        }
    });

    // 2. Sort and merge intervals
    intervals.sort();
    merged = merge_intervals(intervals);

    // 3. Count total coverage
    total = merged.sum(|interval| interval.length());

    // 4. Subtract beacons actually on this row
    total - beacons_on_row.count()
}
```

**Key detail**: Beacons CAN exist, so subtract them from impossible count!

**Result**: 4,876,693 positions

### Part 2: Find the Gap (446.74ms)

**Challenge**: Scan 4 million rows to find ONE uncovered position

**Algorithm**:
```rust
fn find_distress_beacon(sensors: &[Sensor], max_coord: i32) -> i64 {
    for y in 0..=max_coord {  // 4 million iterations!
        intervals = calculate_intervals_at_row(sensors, y);
        intervals.clamp_to(0, max_coord);  // Clip to search bounds

        merged = merge_intervals(intervals);

        // Check three gap locations:
        if merged[0].start > 0 {
            return y;  // Gap at x=0
        }

        for adjacent in merged.windows(2) {
            if adjacent[0].end + 1 < adjacent[1].start {
                x = adjacent[0].end + 1;
                return x * 4_000_000 + y;  // Tuning frequency!
            }
        }

        if merged.last().end < max_coord {
            return max_coord * 4_000_000 + y;  // Gap at x=max
        }
    }
}
```

**Why 446ms**: 4 million rows × (interval calc + sort + merge + gap check)

**Result**: 11,645,454,855,041 (x=2,911,363, y=2,855,041)

## 🔧 Technical Implementation Details

### Manhattan Distance Coverage

**Definition**: `d = |x₁ - x₂| + |y₁ - y₂|`

**Diamond-shaped coverage**: Sensor at (sx, sy) with radius R covers all points within Manhattan distance R

**At row y**:
- Vertical distance used: `|sy - y|`
- Horizontal radius remaining: `R - |sy - y|`
- X-range covered: `[sx - remaining, sx + remaining]`

**Example** (from problem, sensor at (8,7), beacon at (2,10)):
```
Radius = |8-2| + |7-10| = 6 + 3 = 9
At row y=10: vertical_dist = 3, remaining = 6
X-coverage: [8-6, 8+6] = [2, 14]
```

---

### Interval Merging Pattern

**Critical function**:
```rust
fn merge_intervals(intervals: &[(i32, i32)]) -> Vec<(i32, i32)> {
    let mut merged = vec![intervals[0]];

    for &(start, end) in &intervals[1..] {
        let last = merged.last_mut().unwrap();

        if start <= last.1 + 1 {  // Overlapping OR adjacent!
            last.1 = last.1.max(end);  // Extend
        } else {
            merged.push((start, end));  // Gap - new interval
        }
    }

    merged
}
```

**Key insight**: Use `<=  last_end + 1` to merge adjacent intervals:
- `[1, 5]` and `[6, 10]` → merge to `[1, 10]` (adjacent at 5+1=6)
- `[1, 5]` and `[7, 10]` → keep separate (gap at 6)

### Parsing with Negative Coordinate Support

**Challenge**: Handle negative coordinates like `x=-2, y=15`

**Solution**: Split on non-numeric, non-minus characters:
```rust
fn parse_input(input: &str) -> Vec<Sensor> {
    input.lines()
        .map(|line| {
            let nums: Vec<i32> = line
                .split(|c: char| !c.is_numeric() && c != '-')
                .filter(|s| !s.is_empty())
                .filter_map(|s| s.parse().ok())
                .collect();

            Sensor { x: nums[0], y: nums[1], beacon_x: nums[2], beacon_y: nums[3] }
        })
        .collect()
}
```

**Handles**: "x=-2, y=15" → splits to ["", "-2", "", "15"] → filters to [-2, 15]

## 🎓 Lessons Learned

### 1. Sparse Coverage → Intervals, NOT Grids

**Before this problem**:
- Thought about grid problems as requiring grid storage

**After this problem**:
- **Sparse coverage** (large area, few constraints) → **interval arithmetic**
- Intervals are O(n) where n = sensors, not O(width × height)
- Parse (4.6µs) + intervals beats any grid approach

**Lesson**: **Match data structure to problem density!** Dense → grids, Sparse → intervals

---

### 2. Manhattan Distance Creates Diamond Coverage

**The geometry**:
```
        #           ← Radius 2
      #####
    #####S#####     ← Sensor
      #####
        #
```

**Why diamond?**: All points with `|x - sx| + |y - sy| ≤ R`

**At horizontal slice y**:
- Vertical budget: `|sy - y|`
- Horizontal remaining: `R - |sy - y|`
- Forms interval, not grid!

**Lesson**: **Geometric understanding** simplifies computation (interval vs full diamond)

---

### 3. Adjacent Intervals Must Merge

**The bug I almost had**: Only merging overlapping intervals

**Example**:
```
[1, 5] and [6, 10]  → Adjacent at x=5.5 (gap-free)
[1, 5] and [7, 10]  → Gap at x=6
```

**The fix**: Use `start <= last_end + 1` not just `start <= last_end`

**Lesson**: **Integer intervals are different** - adjacent means end+1 == start!

---

### 4. Gap Finding Requires Three Checks

**Part 2 pitfall**: Only checking gaps between intervals

**Complete gap locations**:
1. **Before first interval**: `merged[0].start > 0`
2. **Between intervals**: `merged[i].end + 1 < merged[i+1].start`
3. **After last interval**: `merged.last().end < max_coord`

**Lesson**: **Boundary conditions** are edge cases too!

---

## 📚 Mathematical Concepts Applied

### Manhattan Distance (L₁ Metric)

**Definition**: `d((x₁,y₁), (x₂,y₂)) = |x₁ - x₂| + |y₁ - y₂|`

**Properties**:
- Forms diamond/rhombus coverage (not circles)
- Decomposable: vertical + horizontal independently
- Monotonic: Moving closer in one axis reduces distance

**Application**: Coverage calculation is O(1) per sensor per row!

---

### Interval Merging (Computational Geometry)

**Problem**: Given overlapping/adjacent intervals, find minimal covering set

**Algorithm**: Sort by start, then greedy merge

**Complexity**: O(n log n) for sort, O(n) for merge

**Application**: Coverage queries in O(n log n) instead of O(width)

---

### Tuning Frequency Encoding

**Formula**: `f(x, y) = x × 4,000,000 + y`

**Properties**:
- **Bijective**: Every (x, y) maps to unique frequency
- **Invertible**: `x = f / 4,000,000`, `y = f % 4,000,000`
- **Ordered**: Preserves lexicographic ordering

**Application**: Compact representation of 2D coordinate as single integer!

### Encapsulation via Domain Methods (DDD)

**The question**: Why `sensor.radius()` instead of `manhattan_distance(sensor.x, sensor.y, sensor.beacon_x, sensor.beacon_y)`?

**The answer**: Domain-Driven Design principles!

**Benefits of `radius()` method**:
1. **Ubiquitous Language**: "radius" is the domain term (sensor detection range)
2. **Encapsulation**: Implementation hidden (could cache, validate, change formula)
3. **Semantic Clarity**: Domain concept vs implementation detail
4. **DRY**: Calculation logic in one place, not scattered
5. **Future-Proofing**: Can evolve without breaking callers

**Connection**: This simple method demonstrates core DDD principle - code reflects domain model!
