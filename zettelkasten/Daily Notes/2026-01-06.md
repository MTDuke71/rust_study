## 🔧 **Technical Insights**

### **Algorithm Selection Philosophy**

**When to use brute force vs. mathematical optimization**:
- Brute force acceptable when: Input size is small, implementation is simple, runtime is negligible
- Mathematical formula required when: Input scales dramatically (48M vs 95), constant-time solution available
- Day 6 demonstrates both: Part 1 uses simple iteration, Part 2 needs quadratic formula

### **Floating-Point Precision in Boundary Cases**

**Edge case handling for exact integer roots**:
```rust
if root1.fract() == 0.0 && (root1 as u64 * (time - root1 as u64) == record) {
    (root1 as u64) + 1  // Exclude exact tie with record
} else {
    root1.ceil() as u64  // Round up to next integer
}
```

**Why this matters**: Need strict inequality (> record, not ≥). Floating-point arithmetic can produce exact integer roots, which must be verified and excluded.

### **Counterintuitive Performance Result**

Part 2 is **2× faster** than Part 1 despite handling 152,000× more time values!
- Complexity theory validated: O(1) beats O(n) regardless of n's magnitude
- Quadratic formula: 2 square roots + arithmetic operations
- Brute force: ~300 iterations with multiplication per iteration
- Lesson: Algorithm choice matters more than input size for asymptotic performance
