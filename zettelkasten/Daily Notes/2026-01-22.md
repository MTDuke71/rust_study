## 🔧 **Technical Insights**

### Dynamic Programming: Top-Down vs Bottom-Up Trade-offs

**Performance Comparison** (from demo_bottom_up.rs measurements):
- **Fibonacci(40)**: Top-down 35.2µs | Bottom-up 4.5µs | Optimized 400ns
- **Coin Change(63)**: Top-down 51µs | Bottom-up 5.2µs
- **LCS("ABCDGH", "AEDFHR")**: Top-down 14.8µs | Bottom-up 3.7µs

**Why Bottom-Up is Faster**:
1. **No recursion overhead** - Iterative loop vs function call stack
2. **Better cache locality** - Sequential array access vs HashMap lookups
3. **Predictable memory** - Pre-allocated array vs dynamic HashMap growth
4. **Array indexing** - O(1) direct access vs O(1) hash computation + collision handling

**When Top-Down is Better**:
- Sparse state spaces (many unreachable states) - cache only fills with needed states
- Complex recurrence relations - easier to translate directly from problem definition
- Debugging/understanding - recursive structure matches problem naturally

**Space Optimization Insight**: Bottom-up enables O(n) → O(1) transformations when state only depends on previous k values (e.g., Fibonacci only needs prev2, prev1 values instead of entire array).

### Rust for Rustaceans Ch4: Error Pattern Selection

**Decision Tree for Error Types**:
1. **Use `Option<T>`** when absence of value is natural (e.g., `first_element`, `find`)
2. **Use `Result<T, ()>`** when operation can fail but caller doesn't need error details
3. **Use `Result<T, E>`** with specific error type when caller needs diagnostic information
4. **Use `Result<(), E>`** for side-effect operations (no meaningful value on success)
5. **Use `!` (never type)** for infallible operations on nightly (compiler-proven impossible to fail)

**Thread Panic Pattern**: `Result<T, Box<dyn Any + Send>>` because panics can be any type - requires `.downcast_ref::<&str>()` to inspect panic payload.

**Key Takeaway**: Choose error representation based on what the **caller** needs, not what's easiest to implement.
