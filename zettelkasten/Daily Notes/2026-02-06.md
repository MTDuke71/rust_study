## 🔧 **Technical Insights**

### v1: Rebuild Bitset (O(n×w))
Every window position rebuilt the entire u32 by OR-ing all `w` bytes. Overlapping bytes between adjacent windows were reprocessed. With w=14, this meant 14 OR ops per position.

### v2: Rolling Frequency Counter (O(n))
Add entering character, remove leaving character. Track unique count with conditional logic. Eliminated redundant work but needed 4 branches per slide (freq transitions: 0→1, 1→2, 2→1, 1→0).

### v3: Rolling XOR Bitset (O(n), branchless)
**XOR is its own inverse**: `a ^ b ^ b == a`. XOR toggles a bit — ON for odd count, OFF for even count. In a window of `w` characters, `popcount == w` means `w` distinct bits are ON. Since we have exactly `w` total characters, each must appear exactly once.

**Why XOR beats freq counter**: Two XOR ops (branchless) vs four conditional branches. Modern CPUs with deep pipelines penalize branch mispredictions. In tight inner loops, this matters.

**Why Part 2 benefited most**: 
- v1: Part 2 was 6.9× slower than Part 1 (O(w) inner loop × more positions)
- v3: Part 2 is only 3.3× slower (just more positions, same O(1) per slide)

### Key Learning: Two Kinds of Optimization
1. **Algorithmic**: Change the complexity class (O(n×w) → O(n)) — v1 to v2
2. **Implementation**: Same complexity, lower constant factor (branches → branchless) — v2 to v3
Both matter. The best solution combines the right algorithm with the right implementation.
