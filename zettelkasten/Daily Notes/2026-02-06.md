## 🔧 **Technical Insights**

**Bitset Uniqueness Check**: OR each character's bit position into a u32. If `count_ones()` equals window size, all characters are unique (OR is idempotent — repeated chars don't add new bits).

**Why u32 not u128**: Day 3 needed u128 for 52 values (a-z + A-Z). Day 6 only has lowercase letters (26 values), so u32 (32 bits) suffices and fits in a single register.

**Part 2 is ~7× Slower**: Two factors compound:
- 3.5× more work per window (14 vs 4 OR operations)
- ~3× more positions checked before finding answer (3495 vs 1140)
- Combined: 3.5 × 2 ≈ 7× — matches observed 6.9× ratio

**No Parse Step Needed**: First AoC 2022 day where input is used directly as bytes. `trim().as_bytes()` is the entire "parse" — just a pointer + length. This eliminates an entire category of complexity.

**`.windows()` Iterator**: Produces overlapping slices of fixed size with zero allocation — just pointer arithmetic over the original data. Perfect fit for sliding window problems.

**Parameterized Core**: Both parts use the same `find_marker()` function, differing only in window size constant (4 vs 14). The right abstraction makes the problem trivial.
