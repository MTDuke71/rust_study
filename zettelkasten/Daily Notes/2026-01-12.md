### Rust for Rustaceans Ch3: Flexible Interfaces (Part 1)
- ✅ **Pages 41-44**: Generic Arguments, Object Safety, Dynamic Dispatch
- **Key Insight**: Balance flexibility with pragmatism - don't make everything generic

**1. Flexible Generic Arguments**:
- Pattern: `fn greet(name: impl AsRef<str>)` accepts `&str`, `String`, `Box<str>`, etc.
- User chooses owned vs borrowed - API doesn't force conversions
- Zero runtime cost - compiler monomorphizes per type
- **Integrator approach**: Compose with caller's existing types, no forced allocations

**2. Generic Monomorphization Trade-off**:
- Each type parameter creates separate compiled function
- Fast: Inlined, optimized for specific type
- Binary bloat: `process<T>` called with 10 types = 10 compiled versions
- **Balance**: Use generics for parameters/hot paths, avoid over-generification

**3. Object Safety & Dynamic Dispatch** (`dyn Trait`):
- Enables heterogeneous collections: `Vec<Box<dyn Shape>>`
- Runtime polymorphism via vtable (pointer indirection)
- Trade-off: Slower than generics, smaller binary size
- **When to use**: Mixed-type collections, plugin systems, binary size matters
- **When NOT to use**: Performance-critical tight loops, need generic methods

**4. Design Decision Framework**:
```
Use Generics:          Use dyn Trait:
✅ Function parameters  ✅ Heterogeneous collections
✅ Performance critical ✅ Binary size critical
✅ Type-specific opts   ✅ Runtime polymorphism
✅ Caller's choice      ✅ Plugin architectures
```

**5. Connection to Mission 11**:
- `MemoCache<K, V>` uses generics (not `dyn`) for performance
- Cache lookups in tight loops need inlining
- Each problem uses one state type anyway (no heterogeneity)
- Example validates design: Generic arguments + zero-copy keys = fast

## 🔧 **Technical Insights**

### Dynamic Programming Memoization Patterns
1. **Generic Cache Design**: `HashMap<K, V>` where `K: Hash + Eq, V: Clone`
   - Supports any state type: tuples, structs, string slices
   - Zero-copy keys via generic parameters (no allocations in hot path)
   - Statistics tracking for memoization effectiveness analysis

2. **Top-Down DP Pattern** (canonical 4-step structure):
   ```rust
   // 1. Base case check
   if is_base_case(state) { return base_value(); }
   
   // 2. Memoization check
   if let Some(&cached) = memo.get(state) { return cached; }
   
   // 3. Recursive computation
   let result = compute_from_subproblems(state, memo);
   
   // 4. Cache and return
   memo.insert(state, result);
   result
   ```

3. **Count Accumulation in Recursive DP**:
   - Count starts at 0 at each recursion level
   - Branches add their results: `count += recursive_call(...)`
   - Base cases return 1 (valid path) or 0 (invalid path)
   - Results bubble up through recursion tree summing all valid paths

4. **Iterator Chains for Memory Efficiency**:
   - `.map().filter().sum()` is lazy evaluation (no intermediate array)
   - Each element processed one at a time, immediately added to running sum
   - Avoids allocating Vec<usize> for 1000 intermediate counts
