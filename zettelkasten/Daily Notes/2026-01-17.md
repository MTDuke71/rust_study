### AoC 2023 Day 17: Clumsy Crucible - Complete ⭐⭐

**Problem**: Pathfinding on grid with movement constraints
- **Part 1**: Minimum heat loss path, max 3 consecutive blocks same direction → **1023** (64.3ms)
- **Part 2**: Ultra crucible, min 4/max 10 consecutive blocks → **1165** (182.4ms)

**Algorithm**: Dijkstra's with state-space extension
- **Standard Dijkstra**: Tracks position only → O(V log V)
- **Extended state**: `(position, direction, consecutive_count)` → O((V×D×C) log(V×D×C))
- **Why extended?** Position-only fails - same position reached from different directions with different constraints are DIFFERENT states

**Key Implementation**:
```rust
struct State {
    pos: Coord,           // Where we are
    dir: Direction,       // Direction we're moving
    consecutive: u8,      // How many blocks straight
}
```

**State Space**:
- Part 1: 141×141 grid × 4 directions × 3 max = ~239k states (15-20k processed)
- Part 2: 141×141 grid × 4 directions × 10 max = ~795k states (50-60k processed)
- Part 2 is 2.8× slower for 3.3× more states (sublinear scaling!)

## 🔧 **Technical Insights**

### State-Space Extension Pattern

**Problem**: When position-only Dijkstra fails due to movement constraints

**Solution**: Extend state to include ALL information needed to determine valid next moves
- Standard: `visited: HashSet<Coord>` 
- Extended: `visited: HashMap<State, usize>` where State includes constraints

**Applications**:
- Movement constraints (Day 17: direction + consecutive count)
- Resource tracking (fuel, inventory, keys)
- Direction-dependent costs (wind, slopes)
- Multi-agent coordination

**Mathematical Foundation**: State-space graphs where vertices are (position, constraints) tuples, not just positions. Same physical location can be many different graph vertices based on how you got there.

### Rust for Rustaceans Ch3: Hidden Contracts

**Section 3.3 - Constrained Interfaces**:

**Auto-Traits (Send/Sync)**:
- Marker traits automatically implemented by compiler
- `Send`: Safe to transfer ownership across threads
- `Sync`: Safe to share references `&T` across threads
- Key relationship: if `T: Sync` then `&T: Send`
- **Breaking change**: Removing Send/Sync breaks downstream code
- **PhantomData trick**: `PhantomData<*const ()>` opts-out of Send/Sync (zero cost)
- **Why `*const ()` works**: Raw pointers are NOT Send/Sync, PhantomData inherits this

**SemVer Trick**:
- Supporting multiple dependency versions simultaneously
- Re-export both versions with distinct names
- Allows gradual migration: users upgrade at their own pace
- **Better approach**: Wrap foreign types instead of exposing them
- Use `impl Trait` to hide concrete types (e.g., iterator implementations)
