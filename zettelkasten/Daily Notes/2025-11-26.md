### Phase 1: Problem Analysis & Algorithm Selection

**Problem Understanding**:
- Each claw machine has two buttons (A costs 3 tokens, B costs 1 token)
- Buttons move claw by specific X/Y amounts
- Find minimum tokens to reach prize position (or determine impossible)
- Part 2: Add 10 trillion to prize coordinates (eliminates brute force)

**Algorithm Selection**:
- Recognized as 2×2 linear system: `a*Ax + b*Bx = Px`, `a*Ay + b*By = Py`
- Applied **Cramer's rule** for O(1) closed-form solution
- No mission libraries needed - pure mathematics

**Key Insight**: Linear algebra guarantees at most one solution (for non-parallel lines), so no need to search for "minimum cost" among multiple solutions.

### Phase 2: Implementation Challenges

#### Challenge 1: CRLF Line Ending Parsing

**Initial Approach (Failed)**:
```rust
// Split on double newline for machine blocks
input.split("\n\n")
```

**Problem**: On Windows, line endings are `\r\n`, so double newline is `\r\n\r\n`, not `\n\n`.

**Solution**: Use `.lines()` iterator with line-by-line grouping:
```rust
fn parse_input(input: &str) -> Result<Vec<ClawMachine>> {
    let mut machines = Vec::new();
    let mut current_block = Vec::new();
    
    for line in input.lines() {  // Handles both LF and CRLF!
        if line.trim().is_empty() {
            if !current_block.is_empty() {
                machines.push(parse_machine_from_lines(&current_block)?);
                current_block.clear();
            }
        } else {
            current_block.push(line);
        }
    }
    
    // Don't forget the last block
    if !current_block.is_empty() {
        machines.push(parse_machine_from_lines(&current_block)?);
    }
    
    Ok(machines)
}
```

**Learning**: `.lines()` is the **idiomatic Rust approach** for cross-platform text parsing. It automatically handles:
- Unix line endings (`\n`)
- Windows line endings (`\r\n`)
- Mixed line endings in same file

### Phase 3: Code Refinement & DRY Optimization

#### DRY Optimization: Shared `total_tokens()` Function

**Initial Duplication**:
```rust
pub fn solve_part1(input: &str) -> Result<String> {
    let machines = parse_input(input)?;
    let total: i64 = machines
        .iter()
        .filter_map(solve_machine)
        .map(|(a, b)| calculate_cost(a, b))
        .sum();
    Ok(total.to_string())
}

pub fn solve_part2(input: &str) -> Result<String> {
    let mut machines = parse_input(input)?;
    const OFFSET: i64 = 10_000_000_000_000;
    for machine in &mut machines {
        machine.prize.0 += OFFSET;
        machine.prize.1 += OFFSET;
    }
    
    // Same iterator chain duplicated!
    let total: i64 = machines
        .iter()
        .filter_map(solve_machine)
        .map(|(a, b)| calculate_cost(a, b))
        .sum();
    Ok(total.to_string())
}
```

**After DRY Refactoring**:
```rust
/// Calculate total tokens for all solvable machines
fn total_tokens(machines: &[ClawMachine]) -> i64 {
    machines
        .iter()
        .filter_map(solve_machine)
        .map(|(a, b)| calculate_cost(a, b))
        .sum()
}

pub fn solve_part1(input: &str) -> Result<String> {
    let machines = parse_input(input)?;
    Ok(total_tokens(&machines).to_string())
}

pub fn solve_part2(input: &str) -> Result<String> {
    let mut machines = parse_input(input)?;
    const OFFSET: i64 = 10_000_000_000_000;
    for machine in &mut machines {
        machine.prize.0 += OFFSET;
        machine.prize.1 += OFFSET;
    }
    Ok(total_tokens(&machines).to_string())
}
```

**Benefits**:
- **Single source of truth** for token calculation logic
- **Clearer intent**: Part 2 only differs by offset application
- **Easier maintenance**: Changes to scoring only needed in one place

#### Code Review Discussion: `calculate_cost()` Function

**Question Raised**: Is `calculate_cost(a, b)` necessary when it's just `3 * a + b`?

**Decision**: Keep the function for:
1. **Semantic clarity**: `calculate_cost(a, b)` is self-documenting
2. **Consistency**: Matches the iterator chain pattern
3. **Future-proofing**: Easy to modify if cost formula changes
4. **Readability**: `.map(|(a, b)| calculate_cost(a, b))` reads naturally

**Trade-off**: Slight verbosity vs. clear intent - chose clarity.

#### Sanity Check Removal

**Initial Code** (unnecessary verification):
```rust
fn solve_machine(machine: &ClawMachine) -> Option<(i64, i64)> {
    // ... Cramer's rule calculation ...
    
    // Sanity check: verify the solution actually works
    if a * ax + b * bx != px || a * ay + b * by != py {
        return None;
    }
    
    Some((a, b))
}
```

**Why Removed**:
- Cramer's rule **mathematically guarantees** the solution is correct
- If `a_num % det == 0` and `b_num % det == 0`, the solution is exact
- The check was redundant given the integer divisibility validation
- Cleaner code without defensive checks that can't fail

### Phase 4: Python vs Rust Comparison

**Algorithm Difference**:
- **Python**: Substitution method with float division + `.is_integer()` check
- **Rust**: Cramer's rule with integer modulo for exact divisibility

**Integer Precision Insight**:
```python
# Python approach (potential precision issues at scale)
a = (px * by - bx * py) / det
if float(a).is_integer():
    ...
```

```rust
// Rust approach (exact integer arithmetic)
let a_num = px * by - bx * py;
if a_num % det != 0 {
    return None;  // Not an integer solution
}
let a = a_num / det;
```

**Why Rust's approach is safer**: At 10 trillion scale, floating-point precision loss could cause incorrect `.is_integer()` results.

## 💡 Key Insights & Learning Outcomes

### Cross-Platform Parsing with `.lines()`

**Pattern**: Always use `.lines()` for text parsing in Rust:
```rust
// ✅ Cross-platform (handles \n, \r\n, mixed)
for line in input.lines() { ... }

// ❌ Platform-specific (breaks on Windows)
input.split("\n\n")
```

**Why it matters**: AoC inputs may be copied from web (Unix endings) or edited locally (Windows endings).

### DRY Principle in Competitive Programming

Even in "fast" competitive programming, DRY has value:
1. **Reduces bugs**: Single implementation = single source of errors
2. **Speeds iteration**: Changes apply everywhere
3. **Improves readability**: Intent is clearer

### When NOT to Use Mission Libraries

Day 13 demonstrates that **not every problem benefits from mission libraries**:
- No grid operations → No Mission 6
- No graph traversal → No Mission 8
- Pure mathematics → Simple structs and functions

**Lesson**: Choose the right tool. Sometimes vanilla Rust is the right answer.
